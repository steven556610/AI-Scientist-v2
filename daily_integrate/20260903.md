## 執行過程遭遇之狀況與修復方案

### 狀況 1：`main.py` 陷入無窮迴圈的連線逾時 (Timeout Backoff)
* **現象**：在 Stage 1 (Initial Implementation) 階段，`main.py` 的日誌連續出現 `Backing off backoff_create(...) for 0.9s` 並且停滯不前。
* **原因**：72B 模型在生成長達數百行的實驗架構時，所需運算時間極長（約 10~15 分鐘）。但內建的 OpenAI API Client 預設擁有 **10 分鐘的強制連線逾時限制**。一旦觸發 `APITimeoutError`，系統就會退回並重試，導致無窮迴圈。
* **修復方案**：在 `backend_openai.py` 中，將 `local_coder/` 與 `local/` 的 `openai.OpenAI` client 初始化加入 `timeout=1800.0` (30 分鐘)，給予大型模型充足的推論時間。

### 狀況 2：實驗結果回報時發生 `KeyError: 'summary'`
* **現象**：當第一個實驗 Node 成功執行後，發生崩潰報錯：
  ```
  File "/workspace/ai_scientist/treesearch/parallel_agent.py", line 712, in parse_exec_result
    node.analysis = response["summary"]
  KeyError: 'summary'
  ```
* **原因**：在執行完實驗後，`parallel_agent.py` 會請求模型對執行結果做 Review (定義的格式為 `review_func_spec`)，期望回傳含有 `"summary"` 與 `"is_bug"` 的 JSON。但 72B 偶爾會輸出非標準的 JSON 格式或夾雜純文字。而我們先前在 `backend_openai.py` 寫死的例外錯誤處理 (Fallback)，只針對了畫圖階段 (回傳 `{"plot_analyses": ... }`)，導致系統去讀取 `"summary"` 鍵值時發生找不到的狀況而崩潰。
* **修復方案**：在 `backend_openai.py` 中加入了動態的 `get_fallback_for_spec(spec, text)` 函數，會判斷目前的 `func_spec.name` (如 `"review"` 或 `"plan"`)，動態回傳正確的 JSON 骨架以承載模型的純文字回應。

## 後續執行與維護注意事項

1. **伺服器管理與 Port 衝突**：
   - 務必確保在執行 `main.py` 前，`serve_coder.py` (8002) 和 `serve_vlm.py` (8000) 皆已穩定運作且成功 Loading Weights。
   - 若未來手動中斷任務，請注意 tmux 背後是否有僵屍行程 (Zombie Python Process) 霸佔 Port，這會導致下一次啟動時出現 `[Errno 98] address already in use` 錯誤，需手動 kill PID。
2. **更多潛在的 JSON 解析崩潰**：
   - 雖然已修復 `review` 和 `plan` 的 Fallback，但在後續的 Stage 3 (Writeup) 或 Stage 4 (Review) 階段，若又遇到模型格式不聽話且未命中正則表達式的狀況，可能會因為出現新的 `func_spec` 而導致類似 `KeyError`。屆時請至 `backend_openai.py` 的 `get_fallback_for_spec` 擴充支援的 spec name。
3. **GPU 記憶體監控**：
   - 同時乘載 72B 與 32B 雖然在 GB200 上綽綽有餘，但未來若系統要跑極度吃 VRAM 的大型 Dataset 實驗時，仍需留心系統整體記憶體是否出現 OOM。建議實驗用的 Batch Size 在 `configs/*.yaml` 當中要保持保守。
